## What this is

Next.js web viewer for SuperBrain — a read/browse/search UI over the same backend the mobile app uses (`../backend`, a FastAPI service). This is not the primary client (the Android app is); it's a secondary web interface for browsing, searching, and lightly editing saved posts from a desktop browser.

## Architecture

### Server-only backend access — client code never talks to the backend directly

This is the load-bearing convention in this codebase: **only server-side code (Server Components and Route Handlers) is allowed to call the FastAPI backend.** Client Components (`"use client"`) call this app's own `src/app/api/*/route.ts` handlers, which internally call `src/lib/apiClient.ts`.

- `src/lib/config.ts` reads the backend URL/API key and is commented as **must never be imported from a `"use client"` component** — that's what keeps `SUPERBRAIN_API_KEY` out of the browser bundle. Preserve this boundary when adding new backend calls: add a typed function to `apiClient.ts` and a thin `route.ts` wrapper, don't reach for `fetch` from a client component.
- `src/lib/apiClient.ts` — single `request<T>()` wrapper (adds `X-API-Key`, `AbortController` timeout, per-status custom error messages via `SuperBrainApiError`) with one typed function per backend endpoint (`fetchExport()`, `fetchSemanticSearch()`, `reanalyzePost()`, etc.).
- `src/app/api/*/route.ts` (feed, posts, clusters, taxonomy, topics, reanalyze, refresh, mark-reviewed, update-post, vector-space, thumbnail) are thin: parse request → call `apiClient`/`cache` → return JSON, translating `SuperBrainApiError` into an HTTP response.

### Caching

`src/lib/cache.ts` holds the full `/export` payload and derived clustering "themes" (`src/lib/clustering.ts`) and "vector space" layout (`src/lib/vectorSpace.ts`) in memory on `globalThis` (survives dev HMR). It's invalidated (`invalidateCache()`) after any mutation — `update-post`, `mark-reviewed`, `reanalyze`, `refresh`. If you add a new mutation route, call `invalidateCache()` from it or reads will serve stale data.

### 3D vector-space view (`/space`)

Plots every post as a point in a rotatable 3D scene (`react-three-fiber` + `@react-three/drei`), positioned by projecting its stored embedding down to 3D with `umap-js` (`src/lib/vectorSpace.ts`, seeded for a stable layout across recomputes) and colored by `computeThemes()`'s existing cluster assignment (`src/lib/clustering.ts`) — no backend changes needed, since `/export` already returns embeddings and this reuses the same cached payload every other page uses. A few things worth knowing if you touch it:

- **Clustering is two-pass; the fine pass is threshold-based, the coarse pass is graph community detection.** The fine pass groups near-duplicate posts into tight micro-clusters via `connectedComponents()` (single-linkage/union-find over a `fineThreshold=0.72` cosine threshold) — single-link is fine there because it's only merging near-identical posts, and this output also powers `ThemeAccordion.tsx`'s per-theme sub-groups, so it's left alone. The coarse pass, which merges those micro-clusters into user-facing "themes," used to be threshold-based linkage (single-link, then average-link, then centroid-link) but all three shared a structural flaw: any single global similarity threshold can't be right for both a tight/dense topic and a diffuse/broad one, and a "hub" topic that's weakly similar to lots of unrelated content (e.g. a vague "self-improvement" cluster) isn't stopped from absorbing everything above the cutoff. The coarse pass is now `louvainMerge()`: build a mutual k-nearest-neighbor graph over micro-cluster centroids (an edge only when each of two micro-clusters is among the other's own top-`kNeighbors` most similar — this prunes the one-sided "weakly similar to everything" edges a hub topic accumulates, which a plain/one-sided k-NN graph would keep), then run Louvain modularity optimization (`graphology` + `graphology-communities-louvain`, `louvainResolution` controls granularity) to find communities. This is locally adaptive to density (no single global cutoff), and modularity resists a hub absorbing everything since that requires genuinely dense *mutual* connectivity, not just many weak one-directional similarities. A small/singleton coarse-merge group that ends up under `minThemeSize` gets one more chance before being dropped to "unclustered": a **balanced absorption pass** folds it into an existing theme only if it's unambiguously closest to that one theme (`absorptionThreshold=0.65` similarity, `absorptionMargin=0.03` gap over the second-best theme) — a leftover genuinely between two themes stays unclustered rather than being force-fit. If themes still read as too broad or too fragmented after real usage, `fineThreshold`/`kNeighbors`/`louvainResolution`/`graphMinSimilarity`/`minThemeSize`/`absorptionThreshold`/`absorptionMargin` in `clustering.ts`'s `DEFAULT_OPTIONS` are the knobs to retune. (Louvain, not Leiden, was chosen deliberately — Leiden has no mature JS/TS implementation to lean on, so hand-rolling it was judged a bigger, riskier lift than the gain over Louvain here.)
- **Cluster membership has a soft component for color, even though it's a hard partition for grouping.** Louvain (like the linkage methods before it) still produces a hard partition — a post's `themeId`/`colorSlot` (which theme it's counted under, and which the legend filters by) is still a single hard assignment from its micro-cluster. But `computeVectorSpaceLayout()` separately compares each post's embedding against every theme's centroid; when a post sits nearly as close to a second theme as to its own (see `BLEND_SIMILARITY_MARGIN` / `computeThemeBlend()` in `vectorSpace.ts`), that second theme's color is blended into the point's rendered dot (`VectorSpacePoint.blendColorSlot`/`blendWeight`, mixed via `THREE.Color.lerp` in `VectorSpaceScene.tsx`'s `mixColor()`). This is purely a rendering signal — it doesn't change which theme a post is grouped/counted under.

- **Categorical colors are a separate, extended palette**, not this app's coral/teal/lavender accent tokens — those accents fail CVD-separation validation when checked as a scatter/all-pairs categorical set (see the `dataviz` skill). The palette lives as `--viz-series-1..24` / `--viz-neutral` in `globals.css`, read at runtime via `src/lib/useVizPalette.ts` (three.js material colors need real hex, not a CSS var, so this is the one place that bridges the two). Slots 1-8 are the dataviz skill's validated 8-hue anchor set — only the first 3 are guaranteed distinguishable in every simultaneous on-screen pairing (scatter's "all pairs" case), slots 4-8 pass only the weaker "adjacent pairs" gate. Slots 9-16 and 17-24 are lightness+hue-shifted "light"/"dark" variants of the same 8 anchors — a deliberate departure from the dataviz skill's "never cycle past 8 hues" rule, chosen because this is a single-user app and past 8 categories the always-visible legend/hover label is already doing the real identification work either way (the 24-slot set passes the lightness-band and chroma-floor checks; CVD/contrast checks fail or warn at this count — same secondary-encoding reliance as slots 4-8, just extended further, deliberately, not by oversight). Themes past the 24th (by size) fold into the shared neutral "other" bucket. `VectorSpaceLegend.tsx` defaults to fully expanded (every theme gets a row, not just the top 8), with a toggle to collapse back down to the top 8 (`VISIBLE_CAP`) for a shorter list.
- **Thumbnails are proxied**, never sent inline. `Post.thumbnail` can be a full `data:image/...;base64,...` URI (this backend's actual storage format, not just a documented possibility) — inlining that for every point in the page payload is what balloons it to tens of MB. `src/app/api/thumbnail/[shortcode]/route.ts` decodes/streams it (or redirects for a plain URL) behind a short, cacheable `/api/thumbnail/{shortcode}` path instead; `computeVectorSpaceLayout()` only ever puts that short path on a `VectorSpacePoint`, never the raw thumbnail field.
- Full post detail (for the click-to-open modal) is fetched lazily via the existing `/api/posts?shortcodes=` route, not carried in the initial point payload — `VectorSpacePoint` is deliberately lighter than `ClientPost` (no summary/transcripts/embedding).

### Data fetching pattern — no React Query/SWR/Redux

- Server Components fetch directly via `apiClient`/`cache` at render time (e.g. `src/app/page.tsx`, `src/app/search/page.tsx`).
- Client Components hold state in local `useState` and `fetch` the app's own `/api/*` routes for interactivity (e.g. `src/components/InfiniteFeed.tsx` pagination).
- Mutations from client components typically call `router.refresh()` afterward to get fresh server-rendered data rather than managing client cache invalidation themselves — e.g. the feed component is keyed on `feed.fetchedAt` specifically so a refresh forces a clean remount instead of leaving stale pagination state.

### Types mirror the backend

`src/types/domain.ts` is a single file with all shared types (`Post`, `Collection`, `ExportPayload`, `SearchSemanticHit`, `Theme`, ...), explicitly written to mirror `backend/api.py`'s `/export` and `/search/semantic` response shapes and `backend/core/database.py`'s schema. When the backend's `analyses` table or `/export` shape changes, update this file to match.

### Routes (App Router, `src/app/`)

- `/` — home feed (most recent first)
- `/browse` — filtered feed (category / language / collection)
- `/search` — semantic search
- `/post/[shortcode]` — single post detail
- `/insights` — stats / taxonomy view
- `/space` — 3D vector-space view (every post plotted by embedding similarity, colored by cluster)
- `/ideas` — recurring-tag list (optionally scoped to one theme via `?themeId=`), each row expandable to its source posts with a "Generate study guide" action. **v1 only** — see `src/lib/ideas.ts` below.
- `/boards`, `/boards/[boardId]` — user-curated boards/sub-collections, unrelated to Instagram's own saved-post `Collection`s (see `backend/CLAUDE.md`'s "Boards vs collections"). A board or sub-collection with posts in it also gets a "Generate study guide" action (`BoardDetail.tsx`) — a third one-click generation entry point alongside ideas/themes/clusters below.
- `/study-guides` — a corkboard of study guide **collections** (one per generation request, rendered as a pinned "photo pile" per collection — `StudyGuideCorkboard.tsx`), each pile's title chip colored by what it was generated from (see `source_label` below).
- `/study-guides/[id]` — a single guide's detail view: its role among its siblings (chips to jump between them), its PDF embedded in an `<iframe>`, and its source posts. Deliberately **not** color-coded by source — that distinction is corkboard-only, an overview aid across many piles, not something worth carrying onto one guide's own page (its title chip keeps `CutoutChip`'s normal random color).

### Study guides + Ideas — read before touching either

- **Study guide generation has two UI patterns** — pick-your-own selection vs. one-click from an already-known group:
  - **Selection toolbar** (`src/lib/useStudyGuideSelection.ts` hook + `StudyGuideToolbar.tsx`, same "Select" pattern as `EloquentFeed.tsx`): mounted on `/search` (`SearchResultsWithStudyGuide.tsx`) and inside `/space`'s 3D view (`VectorSpaceView.tsx`) — toggling it there repurposes point clicks into add/remove-from-selection instead of opening the post modal (`highlightedShortcodes` dims everything not selected, reusing the exact mechanism the legend/search-highlight already use; the legend and search box are hidden while active to avoid two "selection" concepts fighting for the same clicks). **Deliberately not on `/` (home feed)** — tried it, decided a flat chronological feed isn't a coherent unit to build a study guide from; a search result, a theme, or a hand-picked 3D selection all have some actual shared thread, the raw feed doesn't.
  - **One-click from a fixed set** (`GenerateStudyGuideButton.tsx`, no selection UI, no toggle): used by `/ideas` rows (`IdeaRow.tsx`, that idea's `shortcodes`, no `groups`), `ThemeAccordion.tsx` (a whole theme's posts, on `/insights`), `/space`'s legend (`VectorSpaceLegend.tsx`, the currently-selected cluster), and `/boards/[boardId]` (`BoardDetail.tsx`, a board's own posts or one sub-collection's posts) — the shortcode set is already known, so there's nothing to pick. The theme-based callers also pass `groups` (each micro-cluster's shortcodes) so a >80-post generation chunks along real sub-topic boundaries instead of an arbitrary split — see `backend/core/study_guide.py`'s `chunk_posts()`.
  - Both paths POST to `/api/study-guide` → `backend`'s `POST /study-guide`, which returns a **collection**, not a single guide; the caller routes to `data.guides[0].id` (always `role="final"`), not `data.id`.
- **`sourceLabel`/`source_label` is the only record of what a generation was made from — deliberately no separate machine-readable type field alongside it.** A `sourceType` prop threaded through `GenerateStudyGuideButton`/`useStudyGuideSelection` into a backend `source_type` column was tried and removed: every caller that would set it already stamps `sourceLabel` with a recognizable prefix (`"Board: ..."`, `"Search: ..."`, `"Theme/Idea/Cluster: ..."`, `"3D space selection"`), so the second field never carried information the first didn't — pure redundancy. `src/lib/studyGuideSource.ts`'s `tapeColorForSourceLabel()` parses that prefix directly instead. Keep this in mind before reaching for "add a matching enum column" again: if a caller can always be made to set both together, the two-field split rarely earns its keep — grep the label prefix instead.
- **`StudyGuideCorkboard.tsx` colors each pile's *title chip* (not the polaroid paper) by `tapeColorForSourceLabel(collection.source_label)`** — `CutoutChip`'s optional `color` prop overrides its normal per-guide seeded random color; every other `CutoutChip` caller (the masthead, the guide detail page's own title) omits it and keeps the random look. Deliberately the title chip, not the polaroid: an earlier version tinted `PolaroidThumb`'s paper border instead and it was invisible in practice — the thumbnail image fills nearly the whole frame, leaving only a thin border to carry the signal. Five fixed colors, never random (`SOURCE_TYPE_TAPE_COLORS` plus `UNLABELED_TAPE_COLOR` for a label with no recognized prefix) — deliberately not `collage.ts`'s full seven-color `seededTapeColor()` palette, both because several of those pastels read as near-identical at a glance and because reusing it would let an "unlabeled" pile coincidentally land on the same hue as a real category, which is indistinguishable from meaningful in practice. `StudyGuideSourceLegend.tsx` reads its swatches straight off the same `SOURCE_TYPE_TAPE_COLORS`/`UNLABELED_TAPE_COLOR` lookup, pinned as its own sticky note (washi tape + hand-lettered swatch list, same primitives as `ScrapbookMasthead`'s subtitle box) at the top of the corkboard, so it can't drift out of sync with what a chip actually renders.
- **A generation response is a collection of 1-N guides, not one doc.** At or under `MAX_STUDY_GUIDE_POSTS` (backend-defined) it's 1 guide. Above it, per explicit user request, the backend runs both a whole-selection pass and a chunked-then-merged pass and persists every intermediate guide (`role`: `final`/`full`/`merge`/`chunk`) as siblings — none are deleted. `/study-guides` and the guide detail page both render this; don't collapse it back down to "one guide per generation" without re-checking `backend/CLAUDE.md`'s "Study guides" section.
- **Every guide is rendered as a PDF, not markdown, in this app.** `Markdown.tsx` is not used for study guides — `/study-guides/[id]` embeds `/api/study-guides/{id}/pdf` in an `<iframe>`, and thumbnails come from `/api/study-guides/{id}/thumbnail` (first page, rasterized). Both are thin server-only proxies (`fetchStudyGuideAsset()` in `apiClient.ts`) to the backend's on-demand PDF/PNG rendering (`core/study_guide_pdf.py`) — necessary because those backend routes require `X-API-Key`, so a browser `<img>`/`<a>` can't hit the backend directly (same constraint `/api/thumbnail/[shortcode]` works around for post thumbnails, except that one can redirect to an unauthenticated `/media` URL — these can't).
- **Ideas (`src/lib/ideas.ts`)**: a ranked list of recurring tags, computed by **pure aggregation over already-stored `Post.tags`** — zero new LLM calls, zero new embeddings, reusing `normalizeTag`/`GENERIC_TAGS` already exported from `clustering.ts`. This was a deliberate cost tradeoff (the user did not want to pay for new embeddings when this was built), not an oversight: it dedups by string match, not by meaning, so two tags phrased differently for the same idea show up as two separate rows. **The planned v2** (already agreed with the user) is real semantic dedup — AI-extracted atomic claims per post, embedded and clustered the way `clustering.ts` already clusters whole-post embeddings — which should replace `computeIdeas()` outright, not extend it, and should also upgrade `backend/core/study_guide.py`'s synthesis (see that module's docstring for the matching note). Do not assume chunk/claim-level embeddings exist anywhere in this codebase yet.
- Both features apply the same low-importance exclusion (posts scoring below 3 on the 1-5 importance rubric are dropped, unscored posts kept) — duplicated as matching constants in `ideas.ts` (`MIN_IDEA_IMPORTANCE`) and `backend/core/study_guide.py` (`MIN_STUDY_GUIDE_IMPORTANCE`) since the two runtimes can't share a constant; keep both in sync by hand if this threshold changes.
